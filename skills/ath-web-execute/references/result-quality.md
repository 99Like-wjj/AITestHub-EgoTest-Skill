# 结果与证据标准

冻结用例给出要验证的业务目标、预期、参考步骤和取证提示。AI 根据现场自主选择路径、动作顺序、工具、证据类型和采集时机。同一个目标可以用不同入口或来源交叉验证。允许合并观察、补查状态或探索相关分支，结果只记录实际验证的固定用例范围。

## 写清现场事实

- 按固定 `runItemId` 与用例批准快照记录。用 `actualActions` 描述实际操作，按现场经过写出入口、数据条件、操作与输出。结果的 `actualObservations` 概括实际事实和整体判定依据。
- `observations` 的每项 `actual` 描述可核查事实，可带 `assertionIds`、`stepOrdinals`、`actionOrdinals`、`evidenceRefs`。步骤和动作的序号从 1 开始，分别指向冻结步骤和本项 `actualActions`。一条观察可支撑多个断言，多条观察也可以共同说明一个断言。证据引用用原 `localEvidenceId`，同时列入结果的 `evidenceRefs`。
- 用 `assertionResults` 按冻结的断言 ID 记录每个必要断言的 `outcome`，需要时填写 `reason`。通过需要所有必要断言的证据。足以证明业务预期被违反时可判失败，同时保留其余断言的真实状态。只验证了预检、保存是否生效不明、环境阻断时，按各断言事实区分无法确认、受阻和未执行。
- 老用例没有结构化断言时，用其原业务预期判断，在观察中关联可以准确定位的参考步骤或实际操作。保留既有历史的原判断和证据缺口。

## 选择和核对证据

- 截图、日志、请求与响应保留采集时的文件字节和实际采集范围。报告说明可以写发生时机、预期差异、业务码、耗时或行级计数，并用证据引用指向原件。保留原件来源，摘要单列。
- 缺入口需要能定位页面状态、角色或已选控件。持久化可由刷新后的读回事实、页面与服务返回的组合，或其他能支持业务判定的原始证据证明。HTTP 200 只说明传输层成功，业务状态由实际返回内容和后续观察判断。
- 采集不到时在 `evidenceGaps` 说明具体缺口。文件登记回执不明确时保留原件，先按同一身份查回执。上传核验与结论依据分别记录。可用 `verify-evidence` 对比本机保留原件和平台文件的实际下载字节。

例如，验证「两个有效成员保存后仍可读到」时，可以直接刷新后在成员页比对前后记录，也可以重新从团队列表打开详情，配合只读响应确认同样的成员身份。记录所走路径、可区分的成员标识和持久化结果，用本轮实际看到的证据支撑。证据关联和业务结论是验收标准，具体操作和取证方式由现场决定。
